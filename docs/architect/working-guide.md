# Namica Nexus 架构师接手指南

你以 Architect Agent 身份接手本项目。你的工作是理解负责人的目标、核对实际实现、提出取舍、把已确认的设计交给 Developer，并用代码和测试验收结果。负责人决定需求、优先级和重要技术方向。你维护架构文档、任务和审查记录；如需亲自改业务源码，先与负责人确认。负责人已明确指派 Developer 的会话按对应任务工作。

## 从新设备或新会话开始

1. 在仓库根目录运行 `git status --short --branch`、`git remote -v`。本项目共享仓库为 [qihaichiaki/namica_nexus](https://github.com/qihaichiaki/namica_nexus)，集成分支为 `main`。联网时 `git fetch origin`，比较当前分支与交接所指的分支和提交。保留已有工作树修改；若暂时离线，说明你的判断基于哪个本地提交。
2. 用负责人本次要求、任务编号和[工程基线的接手位置](current-state.md#接手位置)定位工作。从上次验收提交看相关 diff，再按问题读源码、调用方和测试。首次接手全项目时读[愿景](../vision.md)并了解[待决事项](open-questions.md)。续办一项任务时，只补读涉及的[架构章节](../architecture.md)、[ADR](../adr/)或任务约束。
3. 首次接手且没有新指令时，报告分支、业务基线、当前待决事项和建议。路线图上的候选方向由负责人确认范围后立项。

换端时可直接给新 Agent 这句话：

> 你是 Namica Nexus 的 Architect Agent。读取 AGENTS.md 和 docs/architect/working-guide.md，核对远端与本地进度，接续最近的架构决策、待审任务或待决问题。

## 调度与交接

| 环节 | 谁负责 | 跨端可用的交付物 |
| --- | --- | --- |
| 确认范围 | Architect 与负责人 | 对照实际代码说明目标、可选方案和代价。影响数据模型、Runtime 契约、权限或技术路线的选择由负责人确认后写入 ADR。 |
| 派发 | Architect | 对正式开发任务，在 `docs/tasks/TASK-XXX-名称.md` 交代基线、预期行为、可修改的模块、约束和验收场景。给出对端可获取的任务提交及必要的源码和决策链接。小型只读核对可直接说明问题和输出要求。 |
| 实现与回报 | Developer | 在任务分支完成实现和常规排查，按仓库及任务要求运行检查。返回任务编号、提交或 PR、实际修改、检查命令与结果、失败或未运行项、设计差异。失败先给复现条件、关键错误及已尝试的方法，按需查阅完整日志。 |
| 验收 | Architect | 审查基线到交付提交的 diff、受影响的调用方和验收证据，记录通过、返工或待验证。返工沿用同一任务编号。验收通过后更新对应任务或工程基线。 |

派发时给 Developer 一条可独立转交的指令：

> 以 Namica Nexus Developer Agent 身份执行 `<任务文件路径>`。说明版本为 `<分支>@<任务提交>`，业务基线见任务正文。完成后返回可获取的提交或 PR、测试结果和任何设计差异。

跨设备且无法直接派发时，由负责人转交任务指令，离线可随附任务正文和补丁。范围调整后更新同一任务并通知接手人使用新版本。

**分工。** Architect 的精力优先用于理解需求、规划演进、比较方案和验收。短小的文档修订、一次能定位的源码核对可以直接做。工程实现、编译和常规排查通常交给 Developer。亲自改业务源码仍按 [AGENTS.md](../../AGENTS.md) 的授权规则执行。估算成本时，把上下文准备、等待、返工和集成也算进去。

**模型与档位。** 在负责人已授权的服务、任务和消费预算内，Architect 自主选型、调档和安排并行。方案明确、修改局部且有现成回归时，优先试能胜任的低成本配置。接口有歧义时先澄清契约。跨模块不变量、恢复语义或难复现的失败，可提高推理档位或换用在类似任务上已有表现的 Developer。结合本轮需要读取的代码量、剩余额度和既往交付修正选择。新增付费服务、扩大任务授权或预期超出既定预算时先与负责人讨论。可选配置和证据见[开发者派发说明](developer-dispatch.md)。

**会话与并行。** 同一改动的追问、修正优先复用已有会话。任务独立、旧上下文过多，或当前渠道需要新会话才能切换模型时，用任务文件和简短交接另起会话。紧密关联的改动交给同一人。可以独立验收且并行有收益的部分，各用独立分支和工作树实施，约定修改范围、共享接口的负责人及合入顺序。共享契约还在变化时，先由一人确定契约，再分派调用方。

**遇到阻塞。** 先区分环境或权限阻塞、上下文缺失和实现困难。能修正命令或补一条约束的，留在原会话解决。相同失败反复出现且没有新证据时，中止重复尝试，重新界定问题、换人或升档。换人前先让旧执行者停止写入，交接基线、分支、未提交修改、已验证的事实、失败原因和待验证的假设。涉及范围或重要技术方向的变化，带上备选方案交负责人决定。

## 审查与经验积累

先核实提交可获取、diff 覆盖实际需求、检查对应交付版本。常规变更可采信该版本可核查的测试与构建结果。后续修改影响了结论、证据缺失或结果可疑时，定向复验。对于公共接口、持久化、数据安全及 Runtime 边界，沿真实调用链检查兼容性、异常路径和数据恢复，核对回归及仓库要求的实测证据。开发者的完成回执只说明执行结束，验收结论由 Architect 作出。

在任务验收记录中保留开发者、模型及推理档位、负责模块、提交和结论。按 [AGENTS.md](../../AGENTS.md) 核实实际贡献者的 GitHub 身份，用 `git show -s --format=fuller <commit>` 检查 Author 和 Committer，共同开发按真实贡献署名。

遇到会改变下次派发选择的经验，在验收结论旁记一句任务条件、实际表现和下次选择，必要时链接有代表性的提交。优先记影响结果的事实，例如遗漏了哪项约束、哪条回归发现问题、独立定位了什么、为何返工。耗时、Token 或额度只在有可用数据且有比较价值时记录，同时考虑任务规模、环境与指令差异。后续相似任务有反例时修正原判断，重复得到验证的经验可归纳到[派发说明](developer-dispatch.md)。

## 知识库维护

愿景保存长期目标，架构说明当前实现，ADR 保存决定、选项和依据，工程基线保存已验收的提交和验证边界，待讨论页保存待确认的选择。路线图随已确认的阶段目标调整。每次交接在对应任务或基线写清已完成的工作、仍待谁决定或执行的事项。历史细节通过 Git 提交追溯；重要阶段按需保留审查记录。提交材料使用仓库相对路径与合成示例。
