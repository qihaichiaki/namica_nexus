## 架构判断与风险

**现有设计适合单机 MVP。** Host 独占数据库并持有执行句柄，使关闭浏览器、停止任务和崩溃恢复可以分别处理。平台键与原生键分开，使原生线程不可用时仍能展示真实历史。重大决策及其取舍已分别保存在 [ADR 001](../adr/001-host-and-adapters.md)、[ADR 002](../adr/002-local-storage.md)、[ADR 003](../adr/003-private-codex-home.md)。

| 优先讨论的条件 | 已观察到的限制及影响 |
| --- | --- |
| 引入第二种 Runtime 前 | 生产工厂、初始配置、登录入口和设置表单仍有 Codex 假设，能力标志没有对应的运行分支。不能根据测试工厂可替换就推断另一产品支持同样的恢复、取消及审批。 |
| 需要跨 Runtime 连续性或审计时 | SQLite 可展示业务记录，Codex 依赖自己的线程做推理。当前 Turn 未记模型/Runtime 版本，已处理审批没有持久决定记录；人格也未保留每一历史修订。难以解释一次行为变化的来源。 |
| 出现长会话卡顿时 | Adapter 每次发布截至当前的全文，Store 同步更新整条回复；每次相关通知使 Web 重查会话列表和选中会话的完整快照。合并通知可以减少请求次数，不能减少单次读取量。尚无测得的负载阈值。 |
| 多端重试或自主调度前 | POST 消息没有客户端幂等标识。一个 Turn 已结束、客户端未收到首次响应时，重复发送可能作为新 Turn 受理。属于接口推断，本次没有观察到生产重复执行。 |

阶段结论：V0.1 有可运行和可复核的基础，适合讨论第二种 Runtime 的验证目标。扩展前最值得弄清的是平台可以向用户承诺何种连续性。具体选项见[待讨论事项](open-questions.md)。
