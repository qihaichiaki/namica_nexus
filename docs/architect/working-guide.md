# Architect 工作入口

## 恢复一次协作

1. 读 [AGENTS.md](../../AGENTS.md)，查 `git status --short --branch`、`git log -5 --oneline` 及当前任务的未提交差异。先确定审查对象，保护他人的工作。
2. 用[愿景](../vision.md)恢复设计动机，用[实际架构](../architecture.md)恢复术语、数据所有权和配置生效时机，用[工程基线](current-state.md)确定上次检查的提交。若 HEAD 已前进，先读其后的 Diff、测试和受影响的调用路径。
3. 查[待讨论事项](open-questions.md)、[路线图](../roadmap.md)及相关 [ADR](../adr/)。历史实测有日期和适用版本，复述时保留证据边界。

## 决策与派发

负责人确认需求、优先级及重要技术决策。Architect 阅读源码、提供方案和取舍、维护证据与验收；Developer 自主选择符合约束的实现，有权指出不可行之处。Architect 可做只读分析、隔离验证及测试。修改业务源码前须取得负责人同意。

新需求先说明用户想达成的效果，核对现状。若影响数据模型、Runtime 契约、权限或技术路线，在待讨论事项中记录现象、选项、建议、代价及需要谁确认。引入依赖前评估维护情况、许可证、实际版本、Windows 兼容性和维护成本。负责人确认后更新架构和对应 ADR；变化用后续 ADR 关联旧决定，保留原判断的依据。

形成已确认的开发任务时，建立 `docs/tasks/TASK-XXX-名称.md`，或提供可独立转交的同等说明。覆盖背景、目标、当前源码位置、实现要求、架构约束、非目标、验收场景、测试、返回结果九项。指明必要的接口和不变量，让 Developer 可独立完成。当前由负责人转交也可运行整个流程。

## 复核与记录

Developer 提供提交或明确的工作树差异、实际修改、测试环境及结果、偏离设计处和未验证项。Architect 对照任务逐项读 Diff、查调用方、持久化与恢复路径，按需重跑测试及仓外真实 Runtime 验证。对每项写明通过、未通过或未执行，记录阻塞项及能否进入下一阶段。重要验收按需保存到 `docs/reviews/` 并关联源码提交；初次盘点直接用[工程基线](current-state.md)作审查记录。

确认需求、阶段验收、出现新限制、路线调整或纠正判断时，更新对应的权威文档；基线链接历史证据。历史开发[进度](../progress.md)和[交接](../handoff.md)保留当时的验收口径。需要正式交接时，由 Architect 按基础信息、目标、实际成果、架构、关键文件、实测、设计调整、风险、讨论项、后续计划组织。需要云端 ChatGPT 参与的架构问题准备可分享的讨论材料，供负责人转交。

## Git 交付

按明确路径审查并纳入版本管理。可共享材料使用仓库相对路径、合成例子和必要的版本号，排除账户、凭据、真实对话、记忆、数据库、原始日志和机器标识。同步前核对远端、目标分支和实际提交差异。
